让 Claude 快速搞定一个小任务很容易：你提问、它干活、你检查结果。但长任务完全是另一回事。跨十几个文件的重构、从头构建一个新功能，都可能要花上几个小时。而且你在途中需要纠偏的次数越多，整个过程拖得越久。

好消息是，你手里有很多工具能在这些长会话中帮 Claude 一把。归根结底是两个习惯：在 Claude 动手**之前**界定好工作范围，在它运行**期间**持续纠偏。下面逐一来看。

## 先用计划模式界定工作范围

在 Claude 写下第一行代码之前，先让它拿出一份计划。在计划模式下，Claude 会做调研、探索代码库，并写出一份拟定的实施计划。

拿到计划后，要真的读，不要略读。计划越周密，实施阶段的意外就越少。这也是你及早发现误解的机会：如果 Claude 的计划误解了你的需求，实施结果同样会跑偏，而纠正计划的成本远低于重写代码。

计划模式的价值正在于此：它迫使 Claude 在做任何改动之前先把整个任务想清楚。同时这也意味着，如果 Claude 之后需要压缩上下文，它手里有一份清晰的计划可以依循。

## 在 Claude 工作期间纠偏

Claude 跑起来之后，你有几种办法让它保持在正确的方向上。第一种最明显、也最容易被忘记：直接给它提示词。如果 Claude 正在跑偏或者缺了上下文，你可以向它要一份进度更新。你也可以在执行途中按 esc 中断它，提问、澄清或者改道。

除了提示词，还有两个工具能让你纠偏更有效：压缩（Compact）和回退（Rewind）。

### 压缩（Compact）

压缩会把你的对话总结成一份摘要，用这份摘要作为新的上下文，并删掉旧消息。这样 Claude 就能在长任务中持续工作，而不会撑爆上下文窗口。你可以用 /compact 手动触发压缩，也可以让 Claude 在上下文快满时自动压缩。

所以不要只单独运行 /compact。在命令后面加上指示，告诉 Claude 该如何总结。比如你正在做一个包含多个部分的功能，可能会这样写：

    /compact Focus on the --version flag implementation

（译注：命令后的指示原文为英文，意为“重点保留 --version 标志的实现”。）

你在命令后面写下的任何内容，都会塑造摘要保留什么。这就是你操控压缩的方向盘。

### 回退（Rewind）

当 Claude 走上了错误的路径，你不必靠提示词一点点把它劝回来。回退可以把你带回对话中的某个具体节点，并从那里重新开始。连按两次 esc 打开回退菜单；也可以按 esc 后使用 /rewind 跳回某条具体的消息。

在回退菜单里，你有几个选项：

- 恢复代码与对话——两者一起回滚。
- 恢复对话——只回滚聊天。
- 恢复代码——只回滚文件。
- 从此处起总结——总结检查点之后的一切。适合你中途岔开聊了别的、只想回到主任务时用。
- 总结到此处为止——总结检查点之前的一切。适合前期有一段很长的准备阶段、想把它压缩掉时用。

## 让 Claude 更自主地运行

到目前为止讲的都假设你在亲手盯着、随时纠正。如果你想要更自主的运行方式，有两个功能可以让 Claude 在更少监督下工作：目标（Goal）和循环（Loop）。

### 目标（Goal）

目标用来设定一个完成条件。你描述“做完”是什么样子，Claude 就会跨会话持续工作，直到条件达成或者你叫停它。

例如：

    /goal all tests in src/billing pass, and the type checker reports zero errors

（译注：条件原文为英文，意为“src/billing 中的全部测试通过，且类型检查器报告零错误”。）

要取消它，运行 /goal clear。有一个重要约束：评估器只读取会话记录。所以你的条件必须能在对话中被核查：测试通过、文件存在、代码检查无报错——这些都是 Claude 能从会话记录中验证的事。

### 循环（Loop）

循环会以固定的或自适应的间隔，在回合之间反复运行一个提示词。用它来轮询随时间变化的东西，比如后台任务的状态、一个长时间运行的构建。循环的每次迭代都会占用你的下一条消息槽位，所以循环本身就是一种打断——先运行你的提示词，然后 Claude 再回应你。

要停止一个正在等待下次运行的自适应循环，按 esc 键。固定间隔的循环会一直运行，直到你让 Claude 取消它，或者七天过去。

## 用工作树并行开展工作

到目前为止的纠偏比喻都假设一辆车只有一个方向盘。但当你并行运行多个智能体时，这个比喻就不成立了。每个智能体都有自己的会话、自己的上下文，还可能同时改动同一批文件。

这就是工作树的用武之地。各会话不再互相踩踏，每个会话都获得一份独立的仓库检出副本和自己的分支。你可以这样创建一个：

    claude --worktree feature-auth

因为每个智能体都有自己的工作树，它们不可能互相覆盖对方的改动。会话退出时，它的工作树会被清理掉，它的分支则已准备好接受审查或合并。

还有一个值得知道的文件。仓库根目录下的 .worktreeinclude 文件列出了要复制进每个工作树的、被 git 忽略的文件。这对 .env 文件或本地配置这类东西很有用——你的智能体需要它们，但你又不想把它们提交进 git。

## 小结

应对 Claude Code 的长会话，归结起来就是几个习惯：

1. 先界定工作范围，再纠偏。
2. 定向你的压缩，让摘要保留关键信息。
3. 当 Claude 跑偏时，用回退菜单纠正航向。
4. 当你更能说清“做完是什么样”、而不是步骤时，设定一个目标。
5. 并行工作放在工作树里跑。

做到这些，你就能信任一次长运行，而不必逐步盯着它。
